## 7.1 开发辅助 vs 产品 AI

课程要点：**用 AI 写代码 ≠ 产品需要 AI**。若产品含 AI 功能，需额外说明用途、数据访问范围、预期输出、失败行为、评估样例与成本上限。

### 7.1.1 开发过程是否使用 AI 辅助

| 项 | 内容 |
|---|---|
| 是否使用 | **是** |
| 用在哪些环节 | ① 文档起草与结构对齐（本套 4 份文档、`AGENTS.md`）；② `lab-tools/` 脚本实现（`rssi_survey.py`、`find_espectre.py`、`link_monitor.py` 等）；③ 排障时的假设生成（串口选择、链路摆放、扫描网段掩码）；④ 代码审查与自检清单核对 |
| 团队如何把关 | 凡 AI 主张一律走「提出 → 团队回应 → 理由与验证」流程记入 §7.3；**未经验证的输出不得写成"已完成"**；AI 的提议被否决的记录一并保留（见 AD-04、AD-05、AD-07） |

### 7.1.2 产品本身是否包含 AI 功能

**判定：包含**——产品侧有一个**本地训练、本地运行的小型卷积网络**（覆盖预测模型），**不含**云端 AI/大模型。
（与 v0.1 的判定不同：当时主线是固件内置阈值法的 CSI 运动检测，可写"不适用"；现主线改为 RF Map 覆盖预测，必须按课程要求补齐下列 7 项。）

| 项 | 内容 |
|---|---|
| **用途** | 由少量实测点位（8–15 点）补全出整间房的二维 RSSI 覆盖图，替代"逐点全测"；只做**数值补全**，不做决策、不控制设备 |
| **允许访问的数据** | 仅：① 被指定为**输入点**的坐标与 RSSI；② 房间网格/高度配置。**不允许**访问隐藏实测点、测试集、历史参考地图以外数据；**全程不联网、不上传**（BR-13、NFR-06） |
| **预期输出** | 与网格同尺寸的单通道 RSSI 数值网格（还原为 dBm），以及据此生成的热力图与 MAE/RMSE(dB) 报告（FR-15~FR-18） |
| **失败行为** | ① 网格/高度与训练不一致 → **拒绝出图**并说明（FH-13）；② 隐藏点不足或整份地图 RSSI 全部异常 → 不给结论、不产出空图，提示重采（FH-05、FH-15）；③ 误差与插值基线相当或更差 → **如实报告**，不包装为成功（SM-02）；④ 误差异常小 → 主动输出泄漏自查提示（FH-14） |
| **评估样例** | 同一房间 **≥3 份独立部署**地图 + 固定划分（同 `map_id` 同集合）；测试集只在最后评估一次；报告同一组输入点下的插值基线对比（AC-14）。另含两条**失败样例**：整份地图过强判无效（AC-16）、故意制造泄漏触发自查提示（AC-18） |
| **成本上限** | **0 元/次推理、0 元训练**：模型在本机训练与加载，无云服务、无按次计费（DR-11）。模型体积与加载时间需记录（NFR-09）；若将来必须引入外部推理服务，则因"不联网"约束（BR-13）而不可行 |
| **哪些动作需要用户确认** | 无自动外发、无自动决策。采集、训练、推理均由操作人**显式执行**；是否重采、是否弃用某份地图由人工判断（D-3） |

> 这条判定是**如实**的：它同时意味着我们的产品要接受"AI 功能"对应的更严格审查（数据访问边界、失败行为、评估样例）。这也是 BR-05/BR-06/BR-08/BR-16 存在的原因。

## 7.3 决策与验证记录

### 7.3.1 决策记录表

> 每条写清：AI 提出了什么 → 团队怎么回应 → 理由与**如何验证**。
> AD-01~AD-07 为第一阶段（CSI 运动检测）记录，**保留原始措辞**；AD-08 起为 RF Map 主线的记录。

| ID | AI 建议或主张 | 团队回应 | 理由与验证 |
|---|---|---|---|
| AD-01 | 加入用户登录 | 【待定稿】推迟 | 原型要验证的是感知/预测行为本身；用本地访问即可，登录不改变被测行为。验证方式：完整跑通一次端到端流程，确认无需登录 |
| AD-02 | 用数据库存储事件与配置 | 【待定稿】改为本地文件 | 单场地单设备、数据量小（一份 RSSI 地图 35 行；8 秒原始 CSI 约 200 KB）；文件可直接复查与复现。验证方式：跑通采集→分析并让另一人仅凭文件复现 |
| AD-03 | 无 CSI 时改用 DNS 流量源 | 实测修正 | 固件默认激励打的是**局域网网关**，不依赖外网；实测串口日志 `rx≈100 pps`、`accepted≈100 pps` 即为正常，无需改模式 |
| AD-04 | 调大 `motion_on_hits` 以降低误报 | **否决** | 实测把 on-readings 由 4 调到 12，误报率反而 **5.9%**（对照组 3.4%）；说明时间滤波对本底噪声无效 |
| AD-05 | 用 Edge 打开官方工具页 | **否决** | 官方说明 Device settings / Live motion 在 Edge 中可能不工作；且要求桌面版 **Chrome 151+** |
| AD-06 | 配网始终失败 → 重新烧录固件 | 修正后解决 | 真正原因是**插错串口**；换到板上标 `USB` 的原生口后一次成功（见 BUG-01） |
| AD-07 | 板子贴近路由器信号更好，应尽量靠近 | **否决** | 实测同桌面摆放 RSSI **-22 dBm**，人的走动无法进入几十厘米的链路，表现为"一切正常却测不到运动"；移到 3~5 米后 RSSI **-51~-57 dBm** 才可测量（现为 PRD 证据 E-02） |
| AD-09 | RF Map 点位采集统一用脚本逐点做，并自动留档（均值/中位数/标准差 + 房间与部署元数据） | **采纳** | 任务书要求"以统计值作代表值，同时保留波动"；`lab-tools/rssi_survey.py` 已用本地模拟设备实测（清单→采集→统计→CSV→断点续采全通过），输出可直接进入划分阶段。验证方式：真实设备采一份完整地图并核对 CSV 行数 |
| **AD-10** | 主线由「CSI 运动检测」改为「用少量实测点预测整间房 RSSI 覆盖」 | **采纳（范围收敛）** | 课程立项表与 RF Map 任务书均要求覆盖预测；CSI 运动检测已完成但**不是**本项目的需求主线。验证方式：`docs/01` / `docs/02` 重写为 v1.0，且 03/04 同步（本轮完成） |
| **AD-11** | 加入云端推理 / 公网托管 / 在线大模型 | **否决** | 全程需在局域网内可复现（BR-13），且引入外部推理后成本与数据外发均不可接受；本地小模型足够。验证方式：断网状态下完成"采集→划分→训练→推理→出图" |
| **AD-12** | 用插值结果作为监督答案（因为隐藏点很难留出足够数量） | **否决** | BR-05 明令禁止：插值结果不能充当实测答案，否则等于自己给自己打分。插值只作**基线**或残差方案的初始图。验证方式：AC-12（移走参考答案文件后推理仍能出图）+ AC-18（泄漏自查） |
| **AD-13** | 把归一化/标准化参数用全量数据一起算，能让指标更好看 | **否决** | 会把测试集信息泄漏进模型（BR-07）。验证方式：AC-10 核对参数文件只含训练集统计量 |
| **AD-14** | 直接用 `data.xlsx`（49 点）当训练数据，省一次采集 | **暂缓** | 该表**来源与部署条件未确认**（PRD OQ-02），不能作为训练数据；只可作规模参照。验证方式：核对来源；无法确认则自行重采 |
| **AD-15** | 报告里写"本方案可推广到任意户型" | **否决** | 我们只有一间房间、一个 AP，任务书明确同房间新部署的测试**不能**代替跨房间测试（BR-15）。验证方式：AC-19 核对报告文字限定为"该房间的新部署" |

### 7.3.2 Bug 记录

> 格式固定为：**症状 / 预期 / 调查 / 修复 / 验证**。
> 要点是说明**你们自己验证了什么**，而不是"AI 说修好了"。

#### BUG-01 配网始终不成功

| 项 | 内容 |
|---|---|
| 症状 | 固件烧录成功，但配 Wi-Fi 反复失败；串口读不到输出 |
| 预期 | 设备应能收到配网凭据并连上 2.4 GHz |
| 调查 | 对比两个物理接口：`UART` 口（CP2102N，`/dev/cu.usbserial-10`）读 8 秒无任何输出、Improv 不响应；`USB` 口（原生 USB Serial/JTAG，`/dev/cu.usbmodem101`）复位后输出完整 ESP-IDF 启动日志且 Improv Serial 存在 |
| 修复 | 改用板上标 `USB` 的口进行日志读取与 Improv 配网 |
| 验证 | 命令行配网返回 `Provisioned`，DHCP 分配 IP，且设备信息显示 `ESPectre Native 3.0.0 / esp32c6` |
| 状态 | 已解决 |

#### BUG-02 信号满格但完全测不到运动

| 项 | 内容 |
|---|---|
| 症状 | 设备与网络一切正常，人在附近走动但运动分数无变化 |
| 预期 | 人横穿设备与路由器之间的链路时，状态应切为 motion、分数明显上升 |
| 调查 | 读 RSSI 为 **-22 dBm**，远超合适区间；确认设备与路由器在同一张桌上，无线路径仅几十厘米，人的走动**无法进入该路径** |
| 修复 | 把设备移到与路由器相距 **3~5 米**处，并固定走位线，使身体横穿两者连线 |
| 验证 | RSSI 降到 **-51~-57 dBm**；遮挡段 motion 占比 **100%**、分数均值 **1.0000**；走动段 **84.6% / 0.8828** |
| 状态 | 已解决 |
| **在新主线下的意义** | 这条记录现在是 **PRD 的证据 E-02**：它同时证明了"RSSI 对位置敏感、可用于覆盖建模"，以及"必须规范摆放与接收高度，否则会测到饱和的无效值"——正是 PRD BR-03/BR-04 的来源 |

#### BUG-04 局域网扫描漏掉同网段设备

| 项 | 内容 |
|---|---|
| 症状 | `find_espectre.py` 报"未发现开放 62587 端口的设备"，但设备其实与电脑在同一张网 |
| 预期 | 扫遍电脑所处网段内的所有主机 |
| 调查 | 脚本把默认网段硬编码成 `本机IP/24`；现场 Wi-Fi 掩码为 `255.255.240.0`（**/20**），设备若落在 `10.11.1.x ~ 10.11.15.x` 会被完全漏掉 |
| 修复 | 改为用 `ipconfig getoption en0 subnet_mask` 读**真实掩码**构造网段；地址数超过 4096 时打印提示并回退到本机 `/24`，避免长时间扫描 |
| 验证 | 现场实测：扫描主机数由 254 变为 **4094**（`10.11.0.0/20`），并正确给出"未发现设备"的结论（设备当时确实未上电） |
| 状态 | 已解决 |
| **在新主线下的意义** | 采集脚本每次都要先找设备 IP，"以为设备不在线"会直接把采集挡在第一步（PRD BR-02、FH-01） |

## 7.4 维护规则

- 每次采纳/否决 AI 建议，就补一行决策记录；**当天记**，不要事后补编。
- 每次修 bug，补一条完整记录（含验证证据）；**bug ID 一旦分配不再重编号**（因此本文件保留了 BUG-01/02/04 的原始编号）。
- 与需求相关的变化，同步更新 `docs/02-MVP-PRD.md` 的对应条目，并在最终提交时反映到追溯表。
- 主线切换或范围收敛，必须在三处同时落地：`docs/01`、`docs/02`（权威）与 `docs/03`（实现），并在本文件留一条 AD。
- 本文件与 `AGENTS.md` 保持不矛盾；冲突时以 PRD 与技术设计为准。
